# System Architecture

## Overview

The Inventory Management System follows a layered architecture to separate responsibilities, improve maintainability, and make the application easier to scale.

```text
Client
   │
   ▼
Routes
   │
   ▼
Validators
   │
   ▼
Validation Middleware
   │
   ▼
Controllers
   │
   ▼
Services
   │
   ▼
Models
   │
   ▼
MongoDB Atlas
```

Each layer has a single responsibility and should not contain logic that belongs to another layer.

---

# Folder Responsibilities

## Routes

Routes define the application's API endpoints and connect incoming requests to the appropriate middleware and controller.

Example:

```text
POST /api/v1/auth/register
```

Responsibilities:

- Define endpoints
- Apply middleware
- Forward requests to controllers

Routes should never contain business logic.

---

## Validators

Validators verify incoming request data before it reaches the controller.

Responsibilities:

- Validate request body
- Validate request parameters
- Validate query parameters
- Sanitize user input

Example:

- Email format
- Required fields
- Password length

Validators do not interact with the database.

---

## Validation Middleware

The validation middleware collects validation errors generated by Express Validator.

Flow:

```text
Validators
      │
      ▼
validationResult(req)
      │
      ▼
Errors?
      │
 ┌────┴────┐
 │         │
Yes        No
 │         │
 ▼         ▼
ApiError  Controller
```

---

## Controllers

Controllers handle HTTP requests and responses.

Responsibilities:

- Receive request
- Call services
- Set cookies
- Return API response

Controllers should remain thin and should not contain business logic.

Example:

```text
Request
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Response
```

---

## Services

Services contain the application's business logic.

Responsibilities:

- Database operations
- Authentication
- Authorization decisions
- Inventory calculations
- Purchase order processing

Examples:

- Register user
- Login user
- Update product quantity
- Generate JWT tokens

Services do not know anything about Express, req, or res objects.

---

## Models

Models define the MongoDB collections using Mongoose.

Responsibilities:

- Schema definition
- Relationships
- Validation
- Model methods

Example:

User Model

- Password hashing
- Compare password
- Generate JWT tokens

---

## Database

MongoDB Atlas stores all application data.

Collections:

- Users
- Categories
- Suppliers
- Products
- PurchaseOrders
- InventoryTransactions
- AuditLogs

---

# Authentication Architecture

Authentication uses JSON Web Tokens (JWT).

Two tokens are generated after successful authentication.

## Access Token

Purpose:

- Access protected routes

Contains:

- User ID
- User Role

Lifetime:

15 minutes

Stored as:

HttpOnly Cookie

---

## Refresh Token

Purpose:

Generate new Access Tokens without requiring the user to log in again.

Contains:

- User ID

Lifetime:

30 days

Stored:

- Database
- HttpOnly Cookie

---

## Authentication Flow

```text
Login Request
      │
      ▼
Find User
      │
      ▼
Compare Password
      │
      ▼
Generate Access Token
      │
      ▼
Generate Refresh Token
      │
      ▼
Store Refresh Token
      │
      ▼
Set HttpOnly Cookies
      │
      ▼
Return User
```

# Error Handling

The project uses centralized error handling.

Flow:

```text
Route
   │
   ▼
Controller
   │
   ▼
Service
   │
Error
   │
   ▼
next(error)
   │
   ▼
Global Error Handler
   │
   ▼
Client
```

Benefits:

- Consistent responses
- Cleaner controllers
- Easier debugging

---

# Standard API Response

Every successful response follows the same structure.

```json
{
    "statusCode": 200,
    "success": true,
    "message": "Operation completed successfully",
    "data": {}
}
```

Every error response follows the same structure.

```json
{
    "statusCode": 400,
    "success": false,
    "message": "Validation failed",
    "errors": []
}
```

# Security Decisions

The project follows several security practices.

## Password Hashing

Passwords are hashed using bcrypt before being stored.

Passwords are never stored in plain text.

---

## HttpOnly Cookies

JWTs are stored in HttpOnly cookies.

Benefits:

- JavaScript cannot access tokens.
- Reduces XSS attack risk.

---

## Refresh Token Storage

Refresh Tokens are stored in the database.

Benefits:

- Token revocation
- Secure logout
- Better session management

---

## Role-Based Authorization

Users have one of the following roles.

- Admin
- Employee

Authorization middleware determines whether a user has permission to access a protected resource.

---

# Design Principles

This project follows several software engineering principles.

## Separation of Concerns

Each layer has one responsibility.

- Routes → Routing
- Validators → Validation
- Controllers → HTTP
- Services → Business Logic
- Models → Database

---

## Reusability

Business logic is centralized inside services.

Controllers remain reusable and lightweight.

---

## Maintainability

Each feature is separated into its own module.

Example:

```text
auth/

controller
service
validator
route
```

This makes the project easier to maintain as it grows.
